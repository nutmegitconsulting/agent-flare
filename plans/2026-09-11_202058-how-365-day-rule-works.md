Goal
Explain to an implementer with zero context why the 365-day retention rule does not erase all younger backups, by showing how the tier-matching logic isolates each rule to a specific age band.

Current context / assumptions
- The retention rules form a cascading priority list: tightest window first, widest window last.
- An implementer seeing `365 * 24 * 60 * 60 * 1000` as the final rule might assume it swallows everything.
- The actual behavior depends on "first-match wins" evaluation against the backup's age.

Architecture / proposed approach

The rules form non-overlapping age bands. A backup is evaluated against the rules in order. The FIRST rule whose `maxAgeMs` is greater than or equal to the backup's age wins. The 365-day rule is the last in the list, so it only governs backups that are older than 30 days but younger than 365 days. Every backup younger than 30 days is captured by an earlier rule and never reaches the 365-day rule.

Step-by-step explanation

Task 1: Read the retention tiers in order
File: `src/persistence.ts`

```typescript
const TIERS = [
  { maxAgeMs: 2 * 60 * 60 * 1000,        intervalMs: 5 * 60 * 1000 },        // Tier 0: 0-2 hours old
  { maxAgeMs: 2 * 24 * 60 * 60 * 1000,   intervalMs: 60 * 60 * 1000 },       // Tier 1: 2h-2 days old
  { maxAgeMs: 7 * 24 * 60 * 60 * 1000,   intervalMs: 8 * 60 * 60 * 1000 },  // Tier 2: 2d-7 days old
  { maxAgeMs: 30 * 24 * 60 * 60 * 1000,  intervalMs: 24 * 60 * 60 * 1000 }, // Tier 3: 7d-30 days old
  { maxAgeMs: 365 * 24 * 60 * 60 * 1000, intervalMs: 7 * 24 * 60 * 60 * 1000 }, // Tier 4: 30d-365 days old
];
```

Task 2: Understand first-match evaluation
The `getTier()` function returns the FIRST tier whose `maxAgeMs >= backupAge`:

```typescript
function getTier(ageMs: number): RetentionTier | null {
  for (const tier of TIERS) {
    if (ageMs <= tier.maxAgeMs) return tier;  // FIRST match wins
  }
  return null; // Backup is older than 365 days — delete unconditionally
}
```

Example A — 5-minute-old backup:
```

Tier 0 maxAge = 7,200,000 ms  → 300,000 <= 7,200,000? YES → Tier 0 wins

```

```

Tier 0 through Tier 4: all return NO

```

Task 4: Visualize the age bands as non-overlapping slots
```
Age:     0        2h       2d       7d      30d     365d       ∞
          |--------|--------|--------|--------|---------|--------|
Tier:    [   0    ][   1   ][   2  ][   3  ][   4    ][ delete ]
Interval: every 5m   hourly   8-hourly  daily   weekly
```

A backup lands in exactly one band. The 365-day rule (Tier 4) only occupies the band from 30 days to 365 days. It cannot reach into younger bands because the first-match logic stops at Tier 0/1/2/3.

Task 5: Why the old algorithm looked like it was deleting everything

The old buggy algorithm used a slot-floor approach:
```typescript
const slot = (nextNewerMs // intervalMs) * intervalMs;
```

Every backup — regardless of age — was compared against the interval of the FIRST matching tier. For a 1-day-old backup, Tier 1 (hourly) wins, but the old code still calculated the slot using `intervalMs = 5 * 60 * 1000` from Tier 0 because of a logic error. This made it appear as if the 365-day rule was "erasing everything," when in fact it was the slot-floor bug in the code, not the tier design.

The fixed gap-based algorithm correctly uses the matched tier's interval, so each backup is evaluated against its own band's spacing requirement.

Risks, tradeoffs, and open questions
- The implementer should understand that the order of TIERS matters absolutely. Reversing the array would make the 365-day rule match everything and the whole system would indeed delete all backups except one per week. Never reverse the array.
- If a future requirement adds a rule with a shorter interval but a wider window (e.g. "every 1 minute for 24 hours"), it must be inserted at the TOP of the array (index 0), not appended to the bottom.
